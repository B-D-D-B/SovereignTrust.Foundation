## Proposed bounded implementation

Only the sibling runner and narrowly scoped runner verification/evidence may change after implementation authorization. Revalidate instructions, exact current preimages, selected native packet and AtomicFiles dependency availability first. Keep the original PowerShell runner, provider logic, both app configurations, plans, registrations, native SG/Core and existing histories unchanged. No ExpectedResults inventory, provider repair, retry/continue policy or serializer framework is included.

1. **Capture before abort.** At failed `Initialize-STEnvironment` and `Invoke-PlanPhase`, capture returned canonical Signal Critical entries before the existing throw. Preserve the original operation error and exit 1. A null Signal or thrown exception gets an explicit runtime failure kind, not a fabricated Signal/Critical entry. A failed operation without Critical entries still records its actual failure kind.
2. **Retain partial context.** Before abort, best-effort non-throwing observation reads available current execution-item TestRunId, TestFileName, TestFailures, TestResults and TestRecordEvents. Initialization may have no item. Carry observations out of module scope in an explicitly shared runner-owned diagnostic context even when the invocation throws; do not depend on a successful `$outcome` assignment. Observation failure is secondary and cannot mask the operation failure. Preserve actual partial Boolean assertions separately from runtime diagnostics, with completeness/observation status; zero post-abort observed count must not imply no emitted assertions or a full PASS.
3. **Project bounded safe diagnostics.** RuntimeFailures entries contain Stage, FailureKind, available verified operation identity, textual Level, sanitized bounded Message/string Tags and available UTC entry timestamp. Do not invent EntryId or test identity. Exclude Signal/Pointer/Grid/ReversePointer/Meta, raw ErrorRecord, Exception/InnerException/Data/stack object graphs and arbitrary app/config/plan objects. At most include an allowlisted exception type name. Limit entry count, string/tag lengths and output size explicitly in the implementation; report truncation. Messages and tags must redact credential/token/auth/header/query values, defaulting to a safe category when redaction is uncertain. No arbitrary ToString/property walk. Preserve entry order and do not count propagated diagnostics as assertions.
4. **Bind the actual current run.** Use only observed TestRunId/TestFileName; validate filename grammar, path containment and consistency with current graph/event evidence. Never select the latest file. The current legacy failure payload has no mandatory RunId: bind it by the exact current filename, current execution context and structural equality of its assertion payload to current in-memory TestFailures, then retain all its fields/values. If identity cannot be established, do not merge/overwrite that target. Use a unique invocation-ID-named `st-test-csharp-<InvocationId>-failures.json` fallback, clearly stating TestRunId unavailable/unverified and retaining any safely observed identity as unverified metadata. InvocationId is not TestRunId.
5. **Merge without losing assertion evidence.** Add a reserved top-level RuntimeFailures array and runner-owned identity/completeness metadata while preserving existing Timestamp and every assertion-failure group/envelope/value. Check reserved-name collisions before writing; never reinterpret an assertion group as metadata. An existing runtime section must belong to this invocation and be merged idempotently, not blindly appended on repeated finally paths. Malformed, stale, wrong-run, colliding or concurrently changed content remains unchanged; preserve the diagnostic through a unique fallback plus secondary persistence error, without erasing the conflicting evidence. If no existing failure file exists, seed from safely observed current TestFailures before adding runtime diagnostics; otherwise state assertion context unavailable. Do not create an empty file on a clean run merely because finally executes; retain the normal exporter's behavior.
6. **Persist independently of adapters.** In runner finally, before releasing needed context, write directly to the exact Infrastructure `content/test/results` root, independent of the failing Storage adapter. Use existing AtomicStore Read/Publish revision checking for the exact resource (expected null only for proven absence), a new operation GUID and verified receipt/hash. An unmarked legacy file is readable by AtomicStore; validate its run binding and retain its Read revision rather than treating it as absent. Meet existing local NTFS, reparse/hardlink, byte-limit, owner/authority and recovery prerequisites; retain `.st-publication` intent/recovery evidence. Acquire exclusive runner publication ownership only after the plan's adapter writes have stopped; do not claim the AtomicStore lock fences external bypass writers. Use the established OS authority/ownership contract or stop the dependent publication when it cannot be established. No ACL/global environment changes, new persistence component or weakening of guards is planned. If the existing assembly/authority/root prerequisites cannot be met, record that concrete secondary failure and leave the target unchanged; this is not successful failure-file delivery.
7. **Keep primary failure authoritative.** A failure-file write error or final-report write error cannot overwrite the original error, change exit 1 to success, or prevent conditional environment restoration. Keep primary and secondary errors separate. Attempt the normal unique final report and safe console fallback even when failure-file publication fails; if final-report publication also fails, console still identifies the original error and secondary persistence status without unsafe exception serialization. Startup reports remain unchanged. A runtime failure always prevents whole-run PASS, irrespective of partial true assertions.

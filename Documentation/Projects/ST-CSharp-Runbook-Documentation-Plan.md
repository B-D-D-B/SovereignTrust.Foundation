## Paired-run contract to document

- **Inputs:** pin PowerShell/C# source, tested binary, test definitions, selected plan/phase/case, fixture, app/config, SignalGraph version and dependency identities. Each runtime gets a fresh instance and independent run-owned root with equivalent relative bindings. Bind effective enable flags and no dev/production fallback. Never run a live provider merely because a fixture references its slot.
- **Boundary:** distinguish direct class/helper checks from real condenser dispatch, Memory.Generate, phase/iteration and full runtime paths. Mark stubs/fakes explicitly. Select native supported slices; an unavailable C# path is pending, not a skipped success. Later native external adapters require separate exact ownership/effect contracts.
- **Observations:** compare native false/zero/empty string/null/missing, zero/one/many arrays, graph keys and identity/lineage, registered adapter/slot/instance, hydrated configuration, ordered step/child traces, failure/severity/diagnostics and controlled effect calls. Include failed child propagation and absence of later sentinels/effects. Raw failing results remain failing even for an expected-negative test.
- **Normalization:** allow stable per-run ID mapping, timestamps and test-root prefix substitution only where they are nondeterministic representations. Preserve semantic order, type, multiplicity, parentage, severity, config/resource selection and effect count. Document each allowlisted field and demonstrate that a meaningful changed result would fail comparison. Do not broadly remove logging/fields to obtain equality.
- **Status:** report assertion pass/fail/skip/blocked counts and product outcome separately. A blocked prerequisite, exit 77, missing result, unstarted node or expected-failure marker is not pass. Exact expected-failure behavior can pass its oracle while the raw product result remains failed. Documentation/static checks prove only their stated properties.
- **Evidence:** record paired run IDs, exact commands, source/binary/config identities, raw observations, normalized comparison, first divergence location and actual effect trace. Preserve failures before fixes. Machine receipt format belongs to future harness implementation; document required fields without commissioning a new reporting framework.

## Proposed command interface and batch template

### Incremental native core behind PowerShell wrappers

The proposed migration is feasible as a staged direction: retain thin PowerShell command wrappers, replace supported internal slices with C#, and ultimately deprecate the duplicate inner PowerShell implementation so the production core has one native implementation. C# production code must not call PowerShell to simulate completed native behavior. Document three explicit execution modes through the same eventual wrapper contract: unchanged PS baseline, hybrid selected native boundaries in the existing PS runtime, and final native core. Record the actual backend for every selected boundary/call; hybrid success is partial evidence and cannot substitute for final native execution without legacy internal PS dependence.

In-process substitution is conditional, not a drop-in cast: existing [Plan wrapper](../../Src/PowerShell/Wrappers/Adapters/Condenser/Invoke-PlanCondenser.ps1) uses PowerShell [Signal]-typed parameters and the PowerShell [Signal class](../../../SignalGraph/Src/PowerShell/SignalGraph/Classes/Signal.ps1), while [native Signal](../../../SignalGraph/Src/CSharp/Signal.cs) is SignalGraph.Signal from a distinct assembly/type identity. Before the first hybrid slice, document and check a single live-object compatibility strategy at that exact boundary: canonical shared C# types where wrappers/classes can adopt them safely, or a narrow identity-preserving bridge with explicitly supported members and mutation propagation. Do not pass a cyclic live graph through JSON, assume same-shaped classes are assignment-compatible, or silently copy state between runtimes. If the boundary cannot preserve pointer/jacket/control, object identity, native values and failure semantics, block that substitution and choose a smaller supported boundary; do not invent compatibility.

The selected baseline is PowerShell 7.6.x wrappers and net10.0 Foundation/parity harness on .NET 10. Pin an exact selected .NET 10 SDK and capture the actual PowerShell patch/host runtime per platform; no patch is guessed here. Bind these to dependency identities, assembly identity/load context and module/class parse/load order (including using-module and typed parameter resolution). Existing SignalGraph netstandard2.0 and AtomicFiles net8.0 targets are historical/current dependency facts, not a reason to retarget their projects in this task. Use fresh processes for incompatible old/new type definitions and prevent stale assembly/module reuse. The runbook must require a discriminating host/assembly/type smoke check and representative shared-object mutation/failure checks before hybrid product comparisons. Those checks and wrapper changes are future implementation work, not documentation execution. Preserve public wrapper inputs/outputs at each adopted slice; the final native backend must pass the same selected workflow oracle plus a check that no inner PS implementation was invoked. Document compatibility blockers honestly rather than promising an in-process port on every PowerShell version.

The supported wrapper baseline is PowerShell 7.6.x on .NET 10; do not claim all PowerShell 7.x or automatically accept later releases. For each claimed Windows, Linux and macOS combination, bind the supported OS/version/architecture from the official support matrix and capture the actual host/runtime/SDK. Acceptance requires assembly load/type resolution, shared live graph identity/mutation and selected-plan parity through the wrapper; verify path casing/separators, native process behavior, permissions and native dependencies. Declare platform-specific adapter exclusions explicitly (including Windows/NTFS-only AtomicFiles); unavailable checks block that platform support claim, not documentation or unrelated platform work. Later PowerShell/.NET releases require explicit compatibility tests before a support claim. [PowerShell 7.6 release notes](https://learn.microsoft.com/en-us/powershell/scripting/whats-new/what-s-new-in-powershell-76?view=powershell-7.6) identify .NET 10; use the [PowerShell support lifecycle](https://learn.microsoft.com/en-us/powershell/scripting/install/powershell-support-lifecycle?view=powershell-7.6) for supported host combinations, not an assumption that every OS release is supported.

The runbook must populate a platform acceptance matrix with selected host combinations and actual pass/fail/blocked evidence for the checks above; do not infer support across platforms from one Windows result. Runtime selection is resolved; packaging and individual platform evidence remain future prerequisites.

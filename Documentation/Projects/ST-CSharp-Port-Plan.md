# C# Foundation port: dependency-ordered implementation plan

Proposed future work, 2026-11-12. Function CS-PLAN-01 delivers this plan only. No implementation, runtime acceptance, commit, package publication or deployment is claimed. The coordinator records exact review identity and disposition in [CSharp-Port-Working.md](Working/CSharp-Port-Working.md). SP-01/SP-02, the worker/reviewer cycle and D1–D8 apply through [AGENTS.md](../../AGENTS.md); the plan does not replace them.

## Outcome and boundary

Build a native C# version of Foundation beside the PowerShell implementation, preserving its JSON plan inputs, adapter/slot addressing, Signal/graph relationships, typed values, activity validation, hydration order, result registration, failure propagation and task lifecycle. Work in dependency-ordered waves with functional checks before dependent stages. Do not replace the existing PowerShell module or silently forward the C# execution engine to PowerShell and call that a completed port.

Foundation owns conduction/environment orchestration, mapped routing, condensers, built-in token adapters and EmbeddedFileSystem storage. Concrete providers whose catalog paths name SovereignTrust.Adapters or SDAFusion.Adapters remain those repositories' responsibility. The C# port must expose their dispatch boundary and prove it with controlled adapters; native implementations of those providers are separate dependent work, not implied by this repository's port. Keep unsupported/reserved branches explicit. A plan declaration, catalog row, fake-provider test or passing compilation is not provider or end-to-end acceptance.

## Compatibility design and prerequisites

Use one new `Src/CSharp/Foundation/SovereignTrust.Foundation.csproj` class library and one `Tests/CSharp/SovereignTrust.Foundation.ParityTests.csproj` functional test executable. Initial target net8.0 follows the existing local C# utility and can reference netstandard2.0 SignalGraph. Pin SDK 8.0.428 in an execution-owned local build configuration or invoke that SDK explicitly; do not change repository-wide SDK selection without checking all consumers. Confirm deployment/runtime support and the remaining net8 support window before distributing a binary; retargeting for distribution is a named owner decision, not a hidden port change. Keep the initial harness package-free beyond the production dependency graph, with nonzero exit on any assertion or prerequisite failure and explicit pass/fail/skip counts.

Use SignalGraph's Signal/Graph through a narrow Foundation compatibility layer for differences such as C# Failure property versus PowerShell Failure() method; verify semantics rather than emulate PowerShell syntax. Represent plan objects with ordered, case-insensitive member access where the source requires it, retaining missing versus null, native booleans/numbers/strings and zero/one/many arrays. Use the existing Newtonsoft.Json dependency where it reduces conversion ambiguity; do not add two competing JSON models without a demonstrated need. XML path selection must preserve current predicate and native-value behavior. Preserve plan cloning and graph identity separately: JSON plan cloning is not permission to JSON-clone a live cyclic Signal graph.

Register mapped adapters by family/slot and retain the five-argument dispatch context (slot, activity, conduction Signal, plan, item Signal). A small native adapter interface is necessary for parity tests and future providers; no generalized plugin framework, service container, event bus or DSL is required. Environment bootstrap and library construction must not start listeners or provider activity. Tests inject deterministic clocks/IDs only at nondeterministic boundaries; compare normalized observations, not weakened success booleans.

Before mutation, the execution worker must resolve these bounded prerequisites in the existing Working record:

1. Select exact PowerShell working-tree and SignalGraph baselines; capture hashes, preserve user preimages, and characterize dependencies under SP-01 safeguards. A fresh hash is an observation, not adoption of changed user content.
2. Confirm the existing SignalGraph C# build and required path/serialization/merge behavior. Build with `GeneratePackageOnBuild=false`; no package push. If a missing SignalGraph capability can be bridged without changing semantics, implement the narrow bridge in Foundation and test it. A required sibling change blocks its dependent port stage until separately scoped; do not edit SignalGraph under this plan.
3. Bind the selected test app, templates and local Content slot to run-owned roots; reject default/dev/production fallback and any unregistered adapter. Choose clean process isolation for PowerShell oracle tests to avoid stub class/module contamination.
4. Establish offline restore availability and pin resolved package versions; stop on unavailable packages rather than opportunistically substituting versions. Retain restore/build evidence and dependency identities in the Working record or test receipt, not a duplicate planning ledger.
5. Confirm the deployment target before package/publication work. No NuGet publish, PowerShell replacement, cross-repository edit, cloud/SQL/AI/channel call, listener, shared storage mutation or migration is included in initial implementation authority.

These are implementation prerequisites, not reasons to defer this plan's delivery. Missing provider contracts block only provider-dependent waves. Normal track applies while preserving established semantics with bounded checks; changes to consequential guarantees or unresolved conflicting contracts follow the shared track policy and affected readiness review.
